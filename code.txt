4.1 The Mechanics of "Compute" (Computer Use) in OpenBot
--------------------------------------------------------------------------------
In OpenBot, "compute" refers to agentic computer and browser interaction
(`server/drivers/openai-chat.ts`, `server/drivers/chat-mcp-tools.ts`,
`server/vps-computer.ts`, `server/local-computer.ts`). When an engine or driver
has `computerUse: true`:
1. MCP Tool Mounting: The server mounts high-privilege tools: `computer`
   (mouse clicks, coordinate typing, keyboard combinations, screenshot captures)
   and `browser` (CDP automation, DOM clicking, navigation).
2. Visual Feedback Loop: Each turn captures raw base64 desktop/browser frame
   screenshots (`chatImage`, up to 32MB buffer ceiling via `this.frameBytes`).
3. Turn Expansion: Screenshots and coordinate feedback loops are appended
   iteratively across tool execution steps.

When a driver has `computerUse: false` (or `imageInput: () => false`):
- Computer and browser tools are stripped from the tool catalog during
  `mountChatTools()`.
- Turn images are converted to `textOnly(userTurn.text)` to prevent payload
  rejection.

4.2 Technical Analysis: Why Groq Cannot Handle Compute
--------------------------------------------------------------------------------
File: `server/drivers/groq.ts`
Configuration:
```typescript
export function createGroqDriver(input: DriverInput) {
  return createOpenAIChatRuntime({
    input, driverKind: "groq", apiKey, apiUrl: config.url,
    tools: config.tools, models: () => catalog, refreshModels, reasoning: true,
    reasoningReplayField: "reasoning",
    computerUse: false,        // Explicitly disabled
    imageInput: () => false,   // Vision disabled
  });
}
```

Technical Grounds:
1. Severe Tokens-Per-Minute (TPM) Limits on Groq Free Tier:
   - `llama-3.3-70b-versatile`: 6,000 TPM, 30 RPM, 100,000 TPD.
   - `llama-3.1-8b-instant`: 20,000 TPM, 30 RPM.
   - A single desktop screenshot captured at 1280x1280 resolution converted
     into vision tokens consumes between 1,600 and 2,500 tokens.
   - Combined with the OpenBot system prompt (~1,500 tokens), tool schemas
     (~2,000 tokens for computer MCP schemas), and chat history, Turn 1 consumes
     ~5,000 tokens.
   - On Turn 2 (the verification screenshot), the total tokens in that 60-second
     window exceed 10,000, triggering an immediate HTTP 429 rate limit error:
     `Rate limit reached for model llama-3.3-70b-versatile on tokens per minute (TPM): Limit 6000, Used 8420, Requested 2100.`
2. Lack of Coordinate Fine-Tuning:
   - Groq's open-weights models (Llama 3.3, Qwen) on Groq Cloud lack native
     coordinate prediction fine-tuning, resulting in hallucinated coordinates
     and failed UI interactions.
3. Payload Buffering:
   - Groq Cloud endpoints reject large multipart base64 image request bodies.
Conclusion: Groq is strictly restricted to text-only mode (Tier 1).

5.1 Architecture of the Mobile Connection
--------------------------------------------------------------------------------
The OpenBot mobile architecture consists of:
1. Native Android Companion (`apps/android`):
   Built using Kotlin and Jetpack Compose. Communicates via Server-Sent Events
   (SSE), WebSockets, WebRTC for live audio calls, and remote gestures.
2. Progressive Web App (PWA):
   Mobile web interface accessible directly via browser (`manifest.webmanifest`).

Connection & Pairing Protocol:
- LAN Discovery: Uses Network Service Discovery (NSD/mDNS) advertising
  `_openbot._tcp`.
- Remote Connection: Connects via Tailscale MagicDNS (`100.x.y.z`) or Caddy TLS
  reverse proxy (`https://bot.yourdomain.com`).
- Pairing Handshake (`server/cli-pairing.ts`, `PairingClient.kt`):
  1. Desktop generates a high-entropy 6-digit code or QR code
     (`openmausbot://pair?code=...&server=...`).
  2. Mobile app scans QR code or enters code manually.
  3. Server validates code (`POST /api/auth/pair`) and returns a persistent
     session token (`omb_sess_...`).
  4. Token is stored in Android's Keystore-backed `EncryptedSharedPreferences`.
- Origin Header Security Invariant:
  The companion daemon (`:8810`) strictly rejects requests containing an
  `Origin` header. Because native Android apps do not send an `Origin` header,
  malicious web pages on the local network cannot hijack or query the companion.

6.1 Question 1: "Through my phone, even when my laptop is off, can I open
OpenBot and assign it tasks or things to do?"
--------------------------------------------------------------------------------
Answer:
YES, but ONLY IF OpenBot is running on a 24/7 Cloud VM / Remote Server (VPS),
and NOT if OpenBot was only installed and running locally on your laptop.

Detailed Mechanics:
- If OpenBot is running solely on your laptop:
  When your laptop is turned off or asleep, its CPU halts, network interfaces
  shut down, and the local Node.js server (`:8799`) stops executing. A mobile
  app cannot reach a powered-off device over the network.
- If OpenBot is deployed on a custom Cloud VM (e.g. Hetzner, AWS, GCP, Oracle):
  The OpenBot daemon (`openbot serve`) runs 24 hours a day, 7 days a week.
  Your Android phone connects directly to the Cloud VM over Tailscale or HTTPS.
  You can open the OpenBot Android app, type a prompt, assign complex tasks,
  trigger multi-bot coordination, approve credential/action cards, and review
  artifacts at any time, even while your laptop is completely powered off and
  stowed in a bag.
  When you later turn on your laptop, opening OpenBot connects to the same
  Cloud VM and immediately syncs the entire state.

6.2 Question 2: "What purpose does a remote server have other than hosting
a desktop?"
--------------------------------------------------------------------------------
Answer:
A remote server / cloud VM serves multiple fundamental architectural purposes
beyond hosting a remote desktop for computer use:

1. 24/7 Autonomous Routine & Task Execution:
   OpenBot features an autonomous routine scheduler (`server/routines.ts`,
   `server/scheduler.ts`). The server wakes bots on cron schedules or intervals
   (e.g., hourly database backups, daily morning web scraping, continuous PR
   monitoring). The server executes these turns autonomously using its own
   headless Chrome browser (`npx openmausbot browser install`) and workspace
   containers, with no human presence or desktop required.
2. Persistent Multi-Device Synchronization & State Hub:
   The remote server acts as the single source of truth. All conversations,
   bot configurations, memories (`server/engine-memory.ts`), and artifacts are
   stored in the server's SQLite and JSON databases. Your phone, laptop, and
   tablet all connect to this central hub, ensuring instant continuity across
   all devices.
3. Centralized Asynchronous Notification & Approval Relay:
   When an autonomous bot encounters a question or requires approval (e.g.,
   confirming an API write, deploying code), the server holds the turn and
   dispatches an alert/push notification to your phone. You can review and
   approve the action from your phone without opening a computer.
4. Isolated, Safe Execution Sandbox:
   A cloud server allows bots to execute bash commands, scripts, and untrusted
   code inside Linux containers (Docker / Bubblewrap) without risking your
   personal laptop's files, SSH keys, or host operating system.
5. Persistent Inbound Webhook Listener:
   The server can listen for incoming webhooks from external services (GitHub,
   Stripe, Slack, custom IoT devices), automatically triggering bot turns in
   response to real-world events.
6. Centralized Credential Vault Host:
   The server hosts the encrypted Vault (`server/vault-store.ts`), securely
   providing tokens and credentials to bots as authorized, without distributing
   plain-text API keys across individual client devices.
